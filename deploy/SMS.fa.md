# اتصال پیامک ملی‌پیامک

## تست محلی

در محیط `Development`، فایل اختیاری `backend/AlooGiyah_Api/appsettings.Local.json` خوانده می‌شود. این فایل در Git ثبت نمی‌شود. تنظیمات محیط و آرگومان‌های اجرا بر آن اولویت دارند. کلید واقعی را فقط در همین فایل محلی قرار دهید:

```json
{
  "Auth": { "PhoneOtpEnabled": true, "ExposeOtpCodeInDevelopment": false },
  "Sms": { "Melipayamak": { "ApiKey": "YOUR_API_KEY", "BodyId": 577303 } }
}
```

ترتیب متغیرهای الگوی ۵۷۷۳۰۳: نام، نام خانوادگی، کد. پس از تغییر فایل، API محلی را دوباره اجرا کنید. پذیرش درخواست توسط سرویس و دریافت واقعی پیامک روی گوشی باید جداگانه بررسی شوند.

ارسال از سرور به `https://console.melipayamak.com/api/send/shared/{ApiKey}` با POST انجام می‌شود.
کلید باید فقط در `.env` سرور ذخیره شود و داخل وب یا اپ قرار نگیرد.

تنظیمات `.env` سرور:

```dotenv
PHONE_OTP_ENABLED=true
MELIPAYAMAK_API_KEY=کلید واقعی پنل
MELIPAYAMAK_BODY_ID=524
```

Compose این تنظیمات را به API منتقل می‌کند. پس از تغییر تنظیمات، API باید recreate شود؛ restart به‌تنهایی تنظیمات محیط جدید را اعمال نمی‌کند.

درخواست سرویس شامل `bodyId`، شماره نرمال‌شده `to` و سه `args` به ترتیب نام، نام خانوادگی و کد شش‌رقمی است. در ورود نام‌ها از حساب موجود و در ثبت‌نام از فرم گرفته می‌شوند. دریافت `recId` مثبت به معنی پذیرش درخواست سرویس است، نه تضمین تحویل به گوشی. خطای HTTP، JSON نامعتبر و رسید ناموفق، موفقیت محسوب نمی‌شوند. تکرار خودکار درخواست ارسال انجام نمی‌شود.

جریان API همان `Auth/RequestPhoneCode` و `Auth/VerifyPhoneCode` است؛ فرم‌های پیامکی فعلی وب و اپ از همین مسیر استفاده می‌کنند. ورود رمزعبوری موجود حفظ می‌شود. جدول PhoneOtpChallenges از قبل وجود دارد و این تغییر migration جدید ندارد.

کد پنج دقیقه اعتبار و حداکثر پنج تلاش ناموفق دارد. فاصله درخواست مجدد برای هر شماره و نوع درخواست یک دقیقه است و محدودیت درخواست Auth نیز اعمال می‌شود. فقط هش کد ذخیره می‌شود. پاسخ واقعی API کد پیامک را برنمی‌گرداند. حالت تست بدون ارسال فقط در Development با تنظیم صریح ExposeOtpCodeInDevelopment و بدون کلید پیامک مجاز است؛ Compose آن را غیرفعال می‌کند.

لاگ‌کردن خودکار HttpClient پیامک حذف شده تا کلید داخل URL در لاگ ثبت نشود. خطای سرویس و پاسخ خام آن نیز به کاربر یا لاگ منتقل نمی‌شود.

## بررسی

ساخت Release API موفق بوده است. آزمون‌های آداپتور با HttpMessageHandler جعلی انجام می‌شوند و پیامک واقعی نمی‌فرستند. پس از انتشار، ثبت‌نام یک شماره جدید و ورود یک شماره ثبت‌شده، ترتیب نام‌ها، دریافت واقعی، رد کد اشتباه، انقضا و درخواست مجدد باید بررسی شوند. تأیید واقعی ارسال به تنظیم و فعال‌بودن الگوی ۵۲۴ و موجودی پنل وابسته است.
