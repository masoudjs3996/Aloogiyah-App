# گزارش کش و کنترل درخواست — ۲۲ اکتبر ۲۰۲۶

## سیاست کش

| داده | سرور | مرورگر / اپ |
| --- | --- | --- |
| فهرست، جزئیات و محصولات مشابه کشاورزی | ۶۰ ثانیه | پاسخ HTTP خصوصی تا ۱۸۰ ثانیه؛ محصولات خانه و تخفیف‌ها در حافظه اپ ۱۸۰ ثانیه |
| دسته‌بندی‌ها، درخت و دسته‌بندی‌های خانه | ۲۴ ساعت | پاسخ HTTP خصوصی و داده‌های دسته‌بندی در حافظه اپ ۲۴ ساعت |
| کیف پول، حساب، سفارش، پیام و فایل چت | خارج از کش کاتالوگ | پاسخ‌های فاقد سیاست اختصاصی با `no-store` ارسال می‌شوند |

- تازه‌سازی سرور هنگام اولین درخواست پس از انقضا انجام می‌شود؛ کار زمان‌بندی‌شده برای خواندن بی‌دلیل دیتابیس نداریم.
- محصولات خانه و تخفیف‌ها در اپ هنگام فعال‌بودن صفحه هر سه دقیقه درخواست می‌شوند. بخش تخفیف‌های وب هر سه دقیقه تازه می‌شود و در پس‌زمینه polling ندارد.
- کش مرورگر HTTP است؛ حافظه React Query اپ پس از بستن کامل فرایند تضمین ماندگاری ندارد. داده‌های کاتالوگ در localStorage ذخیره نشده‌اند.
- کلید سرور شامل مسیر، تمام پارامترها و ادعاهای حساب/نقش معتبر است و هش می‌شود؛ داده مدیریت با حساب عادی مشترک نیست. هدرهای `private` و `Vary: Authorization, Cookie` جلوی اشتراک پاسخ خصوصی در کش‌های واسط را می‌گیرند.
- حافظه کش سرور حداکثر ۳۲ مگابایت است؛ پاسخ بزرگ‌تر از یک مگابایت و درخواست با query بزرگ‌تر از ۲۰۴۸ نویسه در آن ذخیره نمی‌شود. خطاها کش نمی‌شوند.
- درخواست‌های هم‌زمان یک کلید با هم ادغام می‌شوند. نوشتن موفق در کنترلر کالا یا دسته‌بندی کش کاتالوگ سرور را خالی می‌کند. نسخه مرورگر تا پایان مهلت خود ممکن است قبلی بماند.
- کش برای نمایش است؛ مسیرهای خرید، محاسبه قیمت و پرداخت از این کش پاسخ داده نمی‌شوند.

- محدودیت عمومی، IP و محدودیت اختصاصی هم‌زمان اعمال می‌شوند. عوض‌کردن توکن برای یک حساب، سهم حساب را بازنشانی نمی‌کند.
- سقف‌های HTTP در `backend/AlooGiyah_Api/appsettings.json` بخش `TrafficLimits` قابل تنظیم‌اند؛ معادل متغیر محیطی مانند `TrafficLimits__IpPerMinute` نیز قابل استفاده است.
- پنجره HTTP ثابت یک‌دقیقه‌ای است؛ نزدیک مرز دو پنجره امکان دو موج درخواست وجود دارد. برای سقف اتصال و تعداد فریم WebSocket تغییر کد لازم است.
- پاسخ محدودسازی HTTP کد ۴۲۹، پیام فارسی، `errorCode=RATE_LIMITED` و `Retry-After` دارد و کش نمی‌شود. مسیر درخواست و زمان انتظار در لاگ ثبت می‌شوند؛ توکن و query ثبت نمی‌شوند.
- تکرار خودکار queryهای ۴۲۹ متوقف می‌شود؛ عملیات مالی خودکار تکرار نمی‌شوند. تلاش دستی همچنان ممکن است، ولی پیش از پایان سهم دوباره ۴۲۹ خواهد گرفت.

## بررسی‌های انجام‌شده

- تست کنترل‌شده سهم ۳۰۰ درخواست، جداسازی دو حساب، سهم مشترک مهمان‌ها، سقف ۱۲۰۰ برای چند حساب روی یک IP و استقلال IP دیگر.
- تست سقف ۶۰ عملیات نوشتن بدون مسدودکردن خواندن همان حساب.
- تست رد IP پیش از رسیدن به middleware بعدی و صحت JSON خطای ۴۲۹ و هدر Retry-After.
- تست استفاده مجدد از کش، تفکیک حساب و query، هدر دسته‌بندی، خارج‌بودن کیف پول، پاک‌شدن پس از ویرایش و جلوگیری از اجرای تکراری هم‌زمان.
- ساخت بک‌اند و typecheck وب و موبایل موفق؛ lint موبایل بدون خطا و lint وب با هفت هشدار موجود درباره img و بدون خطا.
- اجرای عملی در BlueStacks، مرورگر متصل به سرور و آزمایش بار روی محیط انتشار انجام نشده است.

## محدودیت‌های استقرار

این کش و شمارنده‌ها داخل حافظه هر فرایند هستند. راه‌اندازی مجدد آنها را پاک می‌کند؛ در چند replica سهم و پاک‌کردن کش بین سرورها هماهنگ نیست. پیش از استقرار چندسروری باید شمارنده و invalidation توزیع‌شده یا محدودسازی متمرکز در درگاه اضافه شود.

IP واقعی فقط از پراکسی‌های مورد اعتماد تنظیم‌شده در ReverseProxy پذیرفته می‌شود. تنظیم نادرست آن می‌تواند همه کاربران را دارای IP پراکسی نشان دهد؛ اعتماد عمومی به X-Forwarded-For نیز امکان دورزدن محدودیت می‌دهد.

این تغییرات کنترل مصرف در سطح برنامه‌اند؛ جایگزین حفاظت شبکه/CDN/WAF برای حمله حجمی نیستند. سقف IP ممکن است کاربران یک شبکه مشترک را هم محدود کند و باید با آمار واقعی تنظیم شود. ممیزی کامل دسترسی‌ها، امنیت فایل‌ها و تست نفوذ در این کار انجام نشده است.

برای اعمال تغییرات، بک‌اند باید مجدداً راه‌اندازی و نسخه جدید وب و اپ منتشر یا بارگذاری شود.
